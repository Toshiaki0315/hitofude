## L-4. 埋め込み検索

**今やらない理由**（2026-08-23 の実測）。

質問に答えさせるとき（L-2）、材料は FTS5 と `core/keywords.py` で拾って
いる。ここが取りこぼすなら埋め込みが要るが、**取りこぼしが困る規模に
まだ届いていない**。

| | 実測 |
| --- | --- |
| 今の vault | ノート 23 本 / 総 21,753 字（平均 945 字） |
| 全文検索の性能基準（§6.6） | 5,000 ノートで 200ms 未満 |

`keywords.py` の割り切りは分かっている——**ひらがなだけの語は拾えない**
（形態素解析の辞書を `.app` に載せない判断。ADR-0025 と L-2 の記録）。
だが 23 本では FTS5 が拾いきってしまい、**その割り切りが痛む場面が
まだ起きていない**。

**何が起きたらやるか**

- 質問して**出典 0 件**が続く。特に、答えが載っているノートを自分で
  知っているのに拾えない、が繰り返される
- ノートが数百本を超え、言い換え（「予算」と書いたノートを「コスト」で
  探す）で見つからないことが実際に増える

**どちらも「そういう気がする」ではなく回数で見る。** L-2 の実装時にも
同じやり方をした（「予算について何が決まった？」が出典 0 件、という
1 つの実測から `keywords.py` を作った）。

**やるときに払うもの**

- **埋め込みモデルをもう 1 つ取得させる**（`nomic-embed-text` 等）。
  Ollama を入れる手間に上乗せになる
- **ベクトルの置き場**が要る。R9 のとおり `.OboeGaki` の索引ファイルは
  捨ててよいキャッシュなので、そこに置けば作り直せる
- **編集のたびに作り直す**。打鍵の経路には入れない（§6.6）ので、
  保存後の裏側で回す設計になる
- Ollama が無い人には効かない。**FTS5 の道は残したまま**足すことになる

## OCR の行順を整える

**今やらない理由**。ADR-0027 の「やらないこと」で**意図して決めた**もの。

読み取り（macOS の Vision）が返す並びをそのまま使っている。結果、
**スキャンした PDF の表は列ごとに縦に読まれる**（`samples/README.md` の
実測表）。位置で並べ替えれば直せるが、凝ると**「元と違う順で読める」
不具合を自分で作り込む**——段組・回り込み・縦書きの取り違えは、
黙って順序が入れ替わるので**気づきにくい壊れ方**をする。

**構造が要るなら PowerPoint の道がある**（表のまま罫線付きで戻る。
`samples/README.md` の比較表）。表を含む資料は PDF より PPTX で
渡してもらうほうが確かで、そちらは既に動いている。

**何が起きたらやるか**

- **表の入ったスキャン資料を実際に何度も取り込む**ようになり、毎回
  手で直すのが苦になる。1 回や 2 回では引き金にしない
- PPTX で受け取り直す逃げ道が使えない相手（紙でしか来ない）が続く

**やるときに払うもの**

- Vision は文字の**枠の位置**を返せるので、行にまとめて上から下・
  左から右に並べ替えることはできる。同梱の `tools/ocr/ocr.swift` に
  座標を出させる改修が要る
- **段組を読み違えたときに壊れ方が分かりにくい。** 入れるなら、
  段組・表・縦書きのサンプルを先に用意して**実測で比べる**
- ADR-0027 の「やらないこと」を覆すので、**ADR を書き足す**

## 開いた仮身（リンク先の中身をその場に見せる）

**今やらない理由**。[BTRON の実身/仮身](https://qiita.com/satromi/items/72de6f420373e519a075)
にある「開いた仮身」——リンクを置いた場所に、行き先の中身がそのまま
見えている表示（M の検討で外したもの）。

**作れないわけではない。** ブロックの見た目は `editor/painter_overlay.py`
で描いている（R5）ので、そこに行き先の中身を描く道はある。だが**重い** —
描くたびに他のノートを読み、その装飾も解いて、高さを測ることになる。
打鍵の経路に 16ms の予算（§6.6）がある場所で、それをやる理由が今は無い。

**何が起きたらやるか**

- **M-1・M-2 が入って、リンクが実際に増えてから。** 今は links が 1 行
  （2026-08-23 の実測）。中身を見せる相手がいない
- リンクを辿って戻る往復が、実際に煩わしくなる

**やるときに払うもの**

- 打鍵ごとの描画予算（§6.6 の 16ms）を測り直す。**行き先が大きいノート
  だったときが本番**
- 折りたたみ（I-4 で `QTextBlock.setVisible` が使えると分かっている）と
  同じ仕組みが要る可能性が高い。**先に I-4 の実装を見る**
- 「どこまでが自分の文で、どこからが引いてきた文か」を見た目で分ける必要が
  ある。混ざると R1 の感覚（画面の文字＝保存される文字）が壊れて見える

## 続柄で検索する

**今やらない理由**。続柄（M-3）で絞れるのは**リンクの図**だけにしてある。
`Cmd+Shift+F` に `続柄:参考文献` のような書き方を足せば「参考文献として
挙げたもの」を一覧でも引けるが、**検索の書き方をもう 1 つ増やす**ことに
なる。今は `#タグ` と素の言葉の 2 つで、そこに 3 つ目を足す価値が
まだ分からない。

**図のほうで足りている可能性が高い。** 続柄を選んで深さ 3 にすれば、
その関係で繋がったものが一度に見える（実測: 6 点 → 3 点に絞れた）。

**何が起きたらやるか**

- **続柄を実際に使うようになってから。** まず M-3 を数週間使い、
  続柄が付いたリンクが何本になるか見る（M-1 のときと同じ進め方）
- 図では追いきれない——一覧で並べて読みたい、が実際に起きる

**やるときに払うもの**

- `core/searchquery.py` に書き方を足す。**書き方の案内**（`Cmd+Shift+F` の
  ヒント）も増える
- タグと違い、続柄は**リンクに付く**ので「そのノートを探す」と
  「そのリンクを探す」のどちらを返すのかを決める必要がある
