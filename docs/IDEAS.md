## L-4. 埋め込み検索

**今やらない理由**（2026-08-23 の実測）。

質問に答えさせるとき（L-2）、材料は FTS5 と `core/keywords.py` で拾って
いる。ここが取りこぼすなら埋め込みが要るが、**取りこぼしが困る規模に
まだ届いていない**。

| | 実測 |
| --- | --- |
| 今の vault | ノート 23 本 / 総 21,753 字（平均 945 字） |
| 全文検索の性能基準（§6.6） | 5,000 ノートで 200ms 未満 |

`keywords.py` の割り切りは分かっている——**ひらがなだけの語は拾えない**
（形態素解析の辞書を `.app` に載せない判断。ADR-0025 と L-2 の記録）。
だが 23 本では FTS5 が拾いきってしまい、**その割り切りが痛む場面が
まだ起きていない**。

**何が起きたらやるか**

- 質問して**出典 0 件**が続く。特に、答えが載っているノートを自分で
  知っているのに拾えない、が繰り返される
- ノートが数百本を超え、言い換え（「予算」と書いたノートを「コスト」で
  探す）で見つからないことが実際に増える

**どちらも「そういう気がする」ではなく回数で見る。** L-2 の実装時にも
同じやり方をした（「予算について何が決まった？」が出典 0 件、という
1 つの実測から `keywords.py` を作った）。

**やるときに払うもの**

- **埋め込みモデルをもう 1 つ取得させる**（`nomic-embed-text` 等）。
  Ollama を入れる手間に上乗せになる
- **ベクトルの置き場**が要る。R9 のとおり `.hitofude/index.sqlite` は
  捨ててよいキャッシュなので、そこに置けば作り直せる
- **編集のたびに作り直す**。打鍵の経路には入れない（§6.6）ので、
  保存後の裏側で回す設計になる
- Ollama が無い人には効かない。**FTS5 の道は残したまま**足すことになる

## OCR の行順を整える

**今やらない理由**。ADR-0027 の「やらないこと」で**意図して決めた**もの。

読み取り（macOS の Vision）が返す並びをそのまま使っている。結果、
**スキャンした PDF の表は列ごとに縦に読まれる**（`samples/README.md` の
実測表）。位置で並べ替えれば直せるが、凝ると**「元と違う順で読める」
不具合を自分で作り込む**——段組・回り込み・縦書きの取り違えは、
黙って順序が入れ替わるので**気づきにくい壊れ方**をする。

**構造が要るなら PowerPoint の道がある**（表のまま罫線付きで戻る。
`samples/README.md` の比較表）。表を含む資料は PDF より PPTX で
渡してもらうほうが確かで、そちらは既に動いている。

**何が起きたらやるか**

- **表の入ったスキャン資料を実際に何度も取り込む**ようになり、毎回
  手で直すのが苦になる。1 回や 2 回では引き金にしない
- PPTX で受け取り直す逃げ道が使えない相手（紙でしか来ない）が続く

**やるときに払うもの**

- Vision は文字の**枠の位置**を返せるので、行にまとめて上から下・
  左から右に並べ替えることはできる。同梱の `tools/ocr/ocr.swift` に
  座標を出させる改修が要る
- **段組を読み違えたときに壊れ方が分かりにくい。** 入れるなら、
  段組・表・縦書きのサンプルを先に用意して**実測で比べる**
- ADR-0027 の「やらないこと」を覆すので、**ADR を書き足す**
