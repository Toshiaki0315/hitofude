# ADR-0014: デバウンスした「ダーティ範囲の再解析」は作らない

- **日付**: 2026-08-18
- **状態**: 採用（実装済みの判断の追認）
- **覆す対象**: spec.md §6.3 パイプライン図の「デバウンス 400ms で
  block_parser がダーティ範囲を再解析」、§6.6 の「±20 行の再パース」、
  §11 R9 の対策の後半

## 背景

spec §6.3 は編集パイプラインに「デバウンス 400ms で `block_parser` が
ダーティ範囲（前後 ±20 行）を再解析し、1 行では判断できない構造を補正する」
という工程を含めていた。行またぎの構造（コードフェンスの範囲・表・引用の
入れ子）を `highlightBlock()` 単独では判断できない、という懸念（R9）への
対策である。

実装では、この工程は**一度も必要にならなかった**。行またぎの構造は
`classify_line()` + ブロック状態のビットフラグ（`BlockState.encode()` で
int 1 個に詰める）だけで追跡できており、アプリ本体で `parse()`（文書全体の
markdown-it 解析）を表示の補正に使っている箇所は無い。`classify_line` の
消費者は highlighter / outline / slides / document / search で、いずれも
同期呼び出しで足りている。

## 決定

- デバウンスされた再解析パイプラインは実装しない
- 表示の判断は `classify_line()` + `BlockState` に一本化する
- `parse()` は「1 行では判断できない構造の正」を検証するための参照実装
  として core に残し、`parse` と `classify_line` の一致を回帰テストで守る

## 根拠

- Phase 2 の完了条件（10,000 語でカーソル移動が引っかからない、打鍵 p95
  < 16ms）が、この工程なしで達成されている（実測は spec §6.6 と
  highlighter のコメントに記録）
- 工程を足すと「デバウンス前の 400ms 間は表示が誤っている」という
  中間状態が生まれ、テストも複雑になる。ビットフラグ方式は打鍵と同期して
  常に正しい
- ブロック状態が持てない「リストの正確な入れ子」は、表示上は
  ぶら下げインデントの近似で足りており、実害の報告がない

## 影響

- spec §6.3 のパイプライン図・§6.6 の表・§11 R9 に「→ ADR-0014」を追記
- `core/block_parser.py` の「デバウンスした parse() の結果で補正する前提」
  というコメントはこの ADR を指すように読み替える
- 回帰テスト: `tests/core/test_block_parser.py` の parse / classify_line
  一致系のテスト群
